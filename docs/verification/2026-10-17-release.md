# Release verification evidence

Status: **0.1.0 colleague-testing candidate authorized**; the 1 MiB broad-array workflow remains unsupported and 100 MB cases fail. The user explicitly accepted this known limitation for colleague testing; this is an exception to the original release gate, not evidence that the workflow is safe or supported.

## Guardrails and benchmark method

Processing counts tokens and nesting before strict parsing. The current built-in ceilings are 256 nested containers and 100,000 scanner tokens. Exceeding either ceiling blocks inspection without retry; source export remains available. No byte ceiling has been selected. These constants predate this measurement and are not presented as safe capacities. Benchmark fixtures are synthetic broad arrays, nested objects, and strings; cases execute sequentially in Chromium and Firefox. The harness records exact generated bytes, depth, browser/OS/CPU/memory, load and analysis times, usable editor mounting, and failures. It does not measure format/cancel latency, responsiveness probes, or peak browser memory.

## Environment and results

Environment: Linux `7.0.0-38-generic`, Intel Core i7-8565U @ 1.80 GHz, 24,896,471,040 bytes reported system memory; Chromium 156.0.8078.4; Firefox 157.0. Peak browser memory was not measured.

Observed in the generated results: 100 KB and 1 MB broad arrays have >100,000 tokens and are refused (analysis took 1.3–5.9 seconds); the measured deep fixtures were only 1,801 bytes at 300 levels and were refused. The benchmark generator was then corrected to pad deep fixtures to the target size, so those deep measurements do not validate the corrected generator. The 1 MB long string mounted the editor and analysis completed in 1.3–1.7 seconds in both browsers, but this is not the complete format/search/edit/export core workflow. 10 MB strings mounted with analysis times 8.9–14.6 seconds; no full editing workflow was tested. 100 MB broad arrays crashed the Chromium page/browser and timed out in Firefox; 100 MB strings timed out in Firefox, and Chromium exited after its broad-array crash. The generated measurement file is ignored at `benchmarks/generated/results.json`; outcomes are failures, not absent samples.

The task's 1 MB core-workflow release gate is **not met**: the 1 MB broad-array fixture is unavailable under current 100,000-node guardrail. Do not raise the guardrail until representative full-operation resource measurements justify it. This environment provides no manual OS/hardware, native IME, live production network, or native hang-dialog verification. No memory peak or responsiveness probe is claimed.

## 2026-10-18 release-gate follow-up

The exact 1 MiB broad-array fixture (`1,048,575` bytes; `524,287` zero values) was retried with a temporary candidate scanner limit of `1,100,000` tokens. The actual file-open flow and worker analysis accepted it. This is not sufficient to clear the release gate: the full browser workflow did not complete.

In Chromium 156.0.8078.4, the Tree view mounted and the search control accepted a query. Applying a first-element Tree patch through the app's editor patch API updated source to a pretty-printed `2,621,437`-byte document, but CodeMirror then emitted an uncaught `TextNode.lineInner` `TypeError` while updating. The page stopped progressing before Undo, Format, view-switch-back, or Download could be verified. In Firefox 157.0, the same workflow caused the page target to crash during the patch/update. These results are failures, not missing measurements; the remaining core workflow is unverified.

The candidate `1,100,000` scanner limit is rejected and must not be used: it permits a document for which this measured editing path is unsafe. The 1 MiB technical gate remains unmet. The user has explicitly authorized a 0.1.0 release for colleague testing with this limitation disclosed; do not claim 1 MiB broad-array support. Revisit the issue before claiming general large-payload support or a stable release.
